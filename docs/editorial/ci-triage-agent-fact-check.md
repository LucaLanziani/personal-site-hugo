## GitHub Actions and collection

1. `workflow_run` supports the `completed` activity; completion can trigger a separate workflow irrespective of the preceding conclusion, so failure needs a job condition. The listener must exist on the default branch. Its `GITHUB_SHA` and `GITHUB_REF` refer to the default branch. It can access secrets and write tokens even if the upstream workflow could not. GitHub explicitly warns against running untrusted code in it. Source: [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).
2. `permissions` can be specified at workflow or job scope. `contents: read` and `actions: read` are supported; specifying permissions sets unlisted scopes to `none`. There is no step-level `permissions` block. Source: [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
3. The pwn request risk comes from executing attacker-controlled PR code in a context with privileged credentials. Separating untrusted execution from privileged publishing is an established mitigation. Merely checking out files as data is not equivalent to executing them. Source: [GitHub Security Lab: Preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/).
4. Checkout v4 supports `ref`, `path`, and `persist-credentials`; setting persistence to `false` opts out of keeping the authentication configured for later Git commands. The example deliberately uses the documented v4 interface, without claiming it is the newest major. Source: [actions/checkout v4](https://github.com/actions/checkout/tree/v4).
5. `actions/setup-node@v4` accepts `node-version`, including a major-version selector. Source: [actions/setup-node v4](https://github.com/actions/setup-node/tree/v4).
6. `gh run view` accepts a run ID, `--attempt`, and `--log-failed`; the latter selects failed-step logs. Source: [gh run view manual](https://cli.github.com/manual/gh_run_view).
7. `GH_TOKEN` authenticates GitHub CLI and `GH_REPO` selects its default repository. Source: [GitHub CLI environment manual](https://cli.github.com/manual/gh_help_environment). These are used only by the trusted collector.
8. `GITHUB_STEP_SUMMARY` is the per-step path used to add Markdown job summaries; it is a local file rather than a PR-comment API. `GITHUB_PATH`, `GITHUB_WORKSPACE`, and `RUNNER_TEMP` are documented runner variables. Sources: [Variables reference](https://docs.github.com/en/actions/reference/workflows-and-actions/variables), [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-job-summary).
9. Secrets can be supplied through an individual step's `env` rather than the job's environment. This is exposure reduction, not process isolation or protection against persistent code installed by an earlier step. Source: [Using secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Native alternatives

Claims 10–34 support the comparison and the retained [native-CLI example](../examples/ci-triage-native-clis.yml). These adapters are not the primary Pi workflow. Installation commands remain documented references, not immutable release pins.

### Claude Code

10. The supported macOS/Linux/WSL native install command is `curl -fsSL https://claude.ai/install.sh | bash`. The installer also supports release channels and explicit versions. Source: [Advanced setup](https://code.claude.com/docs/en/setup).
11. `-p`/`--print` is noninteractive; `--output-format text` is supported. Source: [CLI reference](https://code.claude.com/docs/en/cli-reference).
12. `--tools` restricts built-in tool availability. `--allowedTools` grants approval for matching tools; it is not itself an exhaustive availability allowlist. Tool names `Read`, `Grep`, and `Glob` are supported; the current default tool set on Linux need not include Grep/Glob, so they are explicitly named. Source: [CLI reference](https://code.claude.com/docs/en/cli-reference).
13. `--tools` does not restrict MCP tools. `--disallowedTools 'mcp__*'` removes MCP tools. `--bare` skips automatic discovery of hooks, skills, commands, subagents, installed plugins, MCP, memory, and CLAUDE.md. Bare mode alone still includes mutation tools, which is why the workflow also supplies the tool list. Source: [CLI reference](https://code.claude.com/docs/en/cli-reference).
14. `ANTHROPIC_API_KEY` is used for API authentication in print mode. Bare mode doesn't load OAuth/keychain credentials and requires API-key authentication or a configured helper. Source: [Environment variables](https://code.claude.com/docs/en/env-vars).

### OpenAI Codex

15. The current native macOS/Linux installer is `curl -fsSL https://chatgpt.com/codex/install.sh | sh`. Source: [Codex CLI](https://learn.chatgpt.com/docs/codex/cli).
16. `codex exec` is the noninteractive interface and defaults to a read-only sandbox. It normally emits progress to stderr and its final response to stdout. `CODEX_API_KEY` is supported for exec authentication; the docs advise against job-level key environments when repository-controlled code runs. Source: [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).
17. `--sandbox read-only` is supported. `--ask-for-approval never` disables escalation prompts while preserving the sandbox. Read-only commands can still run. OS mechanisms enforce command restrictions; current Linux documentation describes `bwrap` and `seccomp`. Command network restrictions don't automatically disable hosted search, apps, or MCP. Source: [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security).
18. `exec` supports `--ignore-user-config`, `--ignore-rules`, and `--skip-git-repo-check`. The first skips `$CODEX_HOME/config.toml`, the second skips execpolicy rule files, and the third permits a directory without Git metadata. Global configuration overrides use `-c key=value`. Source: [Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli).
19. `web_search="disabled"` is a supported configuration value that removes the hosted search tool. Source: [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

### GitHub Copilot CLI

20. The npm package is `@github/copilot`; the official installation command is `npm install -g @github/copilot`, requiring Node.js 22 or later. Source: [Installing Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/install-copilot-cli).
21. For GitHub-hosted access, `COPILOT_GITHUB_TOKEN` is supported and has precedence over `GH_TOKEN` and `GITHUB_TOKEN`. A user-owned fine-grained PAT needs the Copilot Requests **account** permission. Classic PATs aren't supported. BYOK can work without GitHub authentication, so a PAT isn't universally required by the CLI. Source: [Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli).
22. `-p` executes one prompt programmatically. `--available-tools` restricts the model's available tools; `view`, `grep`, and `glob` are documented tool identifiers. `--disable-builtin-mcps` and `--no-custom-instructions` are supported. The reference documents possible session-hint output. Source: [Command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference).
23. `--allow-tool` and `--deny-tool` accept comma-separated permission kinds. `read`, `write`, `shell`, `url`, and `memory` are documented kinds. Deny overrides allow and saved approvals; denied calls don't prompt for permission. These kinds differ from tool identifiers such as `view`. Sources: [Tool controls](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools), [Programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference).

### Cursor CLI

24. The official install command is `curl https://cursor.com/install -fsS | bash`; the workflow reorders the same curl options. The current documented executable is `agent`. Source: [Installation](https://cursor.com/docs/cli/installation).
25. `CURSOR_API_KEY` supplies automation authentication. Source: [Authentication](https://cursor.com/docs/cli/reference/authentication).
26. `--print`, `--mode ask`, and `--output-format text` are documented. Ask mode is described as read-only exploration. `--force` permits commands unless explicitly denied. Sources: [Parameters](https://cursor.com/docs/cli/reference/parameters), [CLI overview](https://cursor.com/docs/cli/overview).
27. The project permissions path is `.cursor/cli.json`. Its JSON has `permissions.allow` and `permissions.deny` arrays. `Read(pathOrGlob)`, `Write(pathOrGlob)`, `Shell(commandBase)`, `WebFetch(domainOrPattern)`, and `Mcp(server:tool)` are documented tokens. Wildcards and absolute paths are supported; deny overrides allow. The example denies both workspace-relative and absolute writes. Source: [Permissions](https://cursor.com/docs/cli/reference/permissions).
28. Cursor's headless page explicitly says changes without `--force` are proposed rather than applied. Its current parameters page says print mode has all tools, including write and shell, and its permissions page says permissions control execution. The draft acknowledges this documentation tension and treats explicit denies as the boundary. Sources: [Headless](https://cursor.com/docs/cli/headless), [Parameters](https://cursor.com/docs/cli/reference/parameters), [Permissions](https://cursor.com/docs/cli/reference/permissions).

### Kiro CLI

29. The official headless GitHub Actions example installs using `curl -fsSL https://cli.kiro.dev/install | bash`. It uses `KIRO_API_KEY`, `kiro-cli chat --no-interactive`, and `--trust-tools=read,grep`. Headless cannot obtain a user's interactive approval for additional tool calls. `--agent <name>` selects a custom agent. Source: [Headless mode](https://kiro.dev/docs/cli/headless/).
30. API-key creation is available for Pro, Pro+, Pro Max, and Power accounts; headless API-key usage consumes subscription credits. Source: [Authentication](https://kiro.dev/docs/cli/authentication/).
31. `.kiro/agents/<name>.json` is a custom-agent path. Custom agents can restrict available tools instead of merely pre-approving them. Source: [Custom agents](https://kiro.dev/docs/custom-agents/).
32. Current `tools` accepts category tags; `read` includes file reading, directory listing, and searching. `includeMcpJson`, `includePowers`, `mcpServers`, `hooks`, and `permissions.rules` are documented fields. The workflow's permission capabilities `fs_read`, `fs_write`, `shell`, `web_fetch`, `web_search`, `mcp`, and `subagent` are documented, as are `allow` and `deny` effects. Source: [Agent configuration reference](https://kiro.dev/docs/custom-agents/configuration-reference/).
33. Current permissions support deny-overrides across scopes, with `deny > ask > allow`. Persistent configuration lives in `permissions.yaml`; the CLI's approval system is distinguished from the Web product's sandbox. Source: [Permissions](https://kiro.dev/docs/permissions/).
34. The V3 migration guide moves persistent trust configuration to capability rules. The headless guide still documents `--trust-tools`, including V3-specific behavior, so the draft retains the flag and adds current capability rules and a restrictive tools list. Sources: [Migration guide](https://kiro.dev/docs/cli/v3/migration-guide/), [Headless](https://kiro.dev/docs/cli/headless/).

## Pi and the external boundary

35. Pi's current npm package is `@earendil-works/pi-coding-agent`; the official install command includes `--ignore-scripts`. The pinned release manifest identifies version 1.0.0, executable `pi`, and Node >=22.19.0. Sources: [Quickstart](https://pi.dev/docs/latest/quickstart), [1.0.0 package manifest](https://raw.githubusercontent.com/earendil-works/pi/v1.0.0/packages/coding-agent/package.json).
36. `--provider` plus `--model`, `--print`, `--no-session`, `--system-prompt`, and the plain tool list `--tools read,grep,find,ls` are documented. The four tools read files, search contents, find paths, and list directories; the list omits `bash`, `edit`, and `write`. Sources: [CLI reference](https://pi.dev/docs/latest/cli), pinned 1.0.0 `--help` and no-key invocation tested locally.
37. Resource controls include `--no-approve`, `--no-extensions`, `--no-skills`, `--no-prompt-templates`, `--no-context-files`, and `--no-themes`. `--no-extensions` disables built-in extensions too; explicitly loading an extension could override it, and the workflow supplies none. Source: [CLI reference](https://pi.dev/docs/latest/cli). All listed flags parsed in the pinned package.
38. Latest docs document `--no-mcp`, but **the installed 1.0.0 package rejects it** with `Unknown option: --no-mcp`. It was removed from the final YAML, and the article explicitly records the discrepancy. MCP customization is disabled through `--no-extensions`, fresh runtime configuration, and no host configuration mount. Source: [CLI reference](https://pi.dev/docs/latest/cli) plus the local runtime rejection. No claim is made that the latest docs match every released package.
39. Pi runs processes with the starting account's permissions; project trust and tool selection are not an OS sandbox. Source: [Security guide](https://pi.dev/docs/latest/security).
40. Official Pi documentation provides a whole-process Docker example using Node, ripgrep, and the current npm package. It distinguishes that from isolating only selected tools. A host home/config mount exposes credentials and customizations; a read-write mount exposes writable host files. Source: [Containerization](https://pi.dev/docs/latest/containerization). Our Docker flags are stricter adaptations, not a vendor-certified configuration.
41. Anthropic and OpenAI API providers use `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`. Pi supports other providers but that is not native-harness parity. Source: [Providers](https://pi.dev/docs/latest/providers). Provider API roots are [Anthropic API](https://platform.claude.com/docs/en/api/overview) and [OpenAI API](https://developers.openai.com/api/reference/overview).
42. `PI_CODING_AGENT_DIR` selects configuration location; `PI_OFFLINE=1` disables startup network activity, not inference; `PI_TELEMETRY=0` overrides telemetry; `HTTP_PROXY` and `HTTPS_PROXY` configure outbound HTTP proxying. Source: [Environment variables](https://pi.dev/docs/latest/environment-variables).
43. Docker supports the example's read-only root filesystem, read-only bind mount, non-root `--user`, capability drop, no-new-privileges, tmpfs, process/memory/CPU limits, and entrypoint override. Root read-only does not prohibit writes to explicitly writable mounts. Source: [docker run](https://docs.docker.com/reference/cli/docker/container/run/). These controls are meaningful filesystem/process limits, not a guarantee against kernel or container-runtime vulnerabilities.
44. An ordinary internal bridge has a host bridge address. `gateway_mode_ipv4=isolated` with `--internal` omits that address. Separate bridge membership lets the proxy reach external destinations while Pi remains on the internal network. Sources: [Gateway modes](https://docs.docker.com/engine/network/port-publishing/#gateway-modes), [Networking overview](https://docs.docker.com/engine/network/).
45. Docker's embedded DNS otherwise forwards external queries. `--dns 127.0.0.1` directs upstream DNS requests to the container's own loopback, where this image runs no resolver; internal `egress` alias lookup still works. Source: [Docker DNS services](https://docs.docker.com/engine/network/#dns-services), verified by an allowed proxy request and blocked external DNS lookup.
46. `NODE_USE_ENV_PROXY=1` enables proxy handling for supported Node HTTP clients. Source: [Node CLI reference](https://nodejs.org/api/cli.html#node_use_env_proxy1). The tested Node 24 image honored it for `fetch` through the workflow proxy.
47. The proxy is authored code in the trusted workflow. It accepts an exact selected `hostname:443` CONNECT target, rejects other targets, resolves a public IPv4 address, and connects to that resolved address. It neither receives provider keys nor mounts source. Those are source inspection and local test findings, not vendor documentation claims. It does not decrypt TLS or inspect provider-bound content.

## Editorial judgments and unresolved evidence

- **Scope change:** the user approved Pi as the primary harness. The main workflow now selects Anthropic or OpenAI with separate credentialed steps; the five-native workflow is preserved as a supplemental example.
- **No supplied YAML:** the initial prompt contained a placeholder. Both examples were authored from the requested architecture.
- **No invented operating history:** the post is a reference implementation. No CI deployment, measured triage result, benchmark, user quote, or authenticated model diagnosis is claimed.
- **Read-only scope:** evidence and the agent's root filesystem are read-only. A tmpfs allows runtime bookkeeping. The host wrapper creates stdout/stderr files; no output file is mounted into Pi. The selected API key remains available inside Pi's process, and malicious output could disclose it. The host runner itself is not immutable.
- **Network scope:** the proxy permits a CONNECT destination, not semantic TLS content. It does not inspect SNI or HTTP requests inside a tunnel; shared upstream addresses and allowed-provider disclosure remain considerations. The proxy has external networking and is a trusted component. Docker/host administration remains outside this boundary. The config intentionally supports only the two specified HTTPS providers.
- **Fork guard:** repository-name equality excludes forks but doesn't prove same-repository branches trustworthy. Snapshot `head_sha` may differ from an upstream generated merge commit; reconcile CI-recorded provenance before claiming exact source correspondence.
- **Prompt injection:** logs and source remain hostile input. The configuration narrows model-accessible actions but cannot guarantee report accuracy or confidentiality. Model context goes to the selected provider.
- **Strength labels:** strong/medium–strong/weakest are engineering assessments of the stated mechanisms, not measured exploit resistance or blanket product rankings. Diagnosis-quality expectations for different failure types are hypotheses, not measured success rates.
- **Supply chain:** the runtime image is required to be digest-pinned. Its sample build uses a mutable default Node tag and apt repositories; use reviewed base digests/build inputs for routine use. The native example retains floating installer endpoints and action tags. Main `checkout@v4` also needs a reviewed commit pin before routine adoption.
- **Version discrepancy:** latest Pi docs and pinned 1.0.0 differ for `--no-mcp`. The final workflow omits the rejected option, and the post's editor note explains why. Updating Pi requires rechecking these restrictions and transports.
- **Cursor discrepancy:** headless/no-force documentation doesn't settle every print-mode mutation path. Explicit permissions deny rules remain necessary; no authenticated native CLI enforcement checks were performed.
- **Account entitlements:** Copilot PAT permissions and Kiro plan requirements were verified in docs, not by obtaining credentials or testing account access. Pi's API-provider steps use neither entitlement.
- **Chosen limits:** 2,000 log lines, 15-minute job, five-minute provider step, 60,000-byte report, and container resource caps are example choices, not measured optima. Byte truncation can cut Markdown or a multibyte character. Submodule and symlink contents are absent from the snapshot.
- **Output handling:** stdout is model-generated text and isn't executed. Stderr isn't published or uploaded; failed diagnoses may therefore require a separate trusted diagnostic collector.
- **End-to-end evidence still missing:** no authenticated provider diagnosis, registry publication/pull by GitHub Actions, or actual failure-triggered Actions run. The local tests cover documented flags and specified container limits, not model quality or every possible bypass.
